- Current expected damage per attempted hit is `A × (1 + rank/100) × (1 + ammo/100) × activeEffectMultiplier × (1 + battleBonus/100) × (0.5 + 0.5p + p×c×C/100)`. ## Network and cache contract

- All API traffic originates in `background.js`, using GET plus URL-encoded `input` against the selected, fixed Official/Gateway base. Official remains the default. Bearer authorization is retained; Gateway additionally receives `X-API-Key` as required by its router. See T005 below for compatibility routing and 429 fallback.
- Batch cache misses use comma-separated procedures, `batch=1`, and indexed input: `{"0":{"regionId":"..."},"1":{"countryId":"..."}}`. A batch with one miss becomes a single request. Results retain the caller's order, including cache hits.
- Procedure names are constrained to `namespace.get...` read methods plus the explicit read-only exception `inventory.fetchCurrentEquipment`. Arbitrary hosts, paths, and HTTP methods cannot be supplied through messages.
- The client unwraps standard tRPC `{result:{data:...}}` envelopes. Every returned envelope must succeed before any new batch results are cached. Returned `data` is otherwise preserved as received.
- T005 registers procedure-specific TTLs of 30/60/180 seconds (table below). Other procedures retain group defaults: 60 seconds for live reads, 300 seconds for `region`/`country`, and 60 seconds otherwise.
- Group TTLs are configurable in the popup. Precedence is batch call TTL, request `options.ttlSeconds`, registered procedure TTL, then group TTL. TTL values are integer seconds from 0 to 86400. Zero disables cache reads/writes and removes an existing matching entry after a successful fetch. Registered procedures therefore retain their defaults when only a group TTL changes.
- `forceRefresh: true` bypasses cache reads, while still writing successful responses if TTL is positive. A shorter requested TTL also rejects entries older than that requested lifetime.
- Each request times out after 15 seconds. Cookies are omitted and redirects rejected. HTTP, network, tRPC, and response-shape failures return sanitized errors and are never cached. Compatible Official HTTP 429 responses retry once through Gateway; no other automatic retries or stale-response fallback are implemented.
- Operations are serialized in one service-worker queue so cache clears and token changes cannot race an earlier fetch. The MV3 listener returns `true` to keep asynchronous message responses open.
- Expired entries remain inspectable until cleared or replaced; they are never served. Cache size is subject to Chrome's normal local storage quota. There is no automatic eviction.

The game publishes its API schema at [WarEra OpenAPI](https://api2.warera.io/openapi.json) and [API docs](https://api2.warera.io/docs/). Repository instructions require GET even where the published schema labels procedures POST.

## Message-passing schema

Use `chrome.runtime.sendMessage({type, ...fields})` from the extension. Every response is one of:

```js
{ ok: true, data: /* result below */ }
{ ok: false, error: { code: "ERROR_CODE", message: "Readable description" } }
```

| Type | Request fields | Successful `data` |
| --- | --- | --- |
| `WE_AGO_SETTINGS_GET` | None | `{hasToken, userId, apiProvider, ttls}` |
| `WE_AGO_SETTINGS_SAVE` | Optional `token`, `userId`, `apiProvider`, `ttls` | `{hasToken, userId, apiProvider, ttls}` |
| `WE_AGO_DISPLAY_GET` | None; popup or WarEra content context | `{marketFontSize}` |
| `WE_AGO_DISPLAY_SAVE` | `marketFontSize` integer 7–14; popup only | `{marketFontSize}` |
| `WE_AGO_FEATURES_GET` | None; popup or WarEra content context | Current independent feature flags (see `we-ago:features`) |
| `WE_AGO_FEATURES_SAVE` | `features`: partial object of known boolean flags; popup only | Merged feature flags |
| `WE_AGO_PLAYER_SUMMARY` | None; uses saved token/user ID | `{state: "setup"}` or the summary below |
| `WE_AGO_QUERY` | `procedure`, optional `input` (object, default `{}`), `options` | `{data, cached, key, createdAt, expiresAt, provider}` |
| `WE_AGO_BATCH` | `calls: [{procedure, input?, ttlSeconds?}]`, optional `options` | Array of query results, in input order |
| `WE_AGO_CACHE_LIST` | None | `[{key, procedure, createdAt, expiresAt, expired, provider}]`, newest first |
| `WE_AGO_CACHE_CLEAR` | None | `{removed: number}` |

Query options: `{ttlSeconds?: number, forceRefresh?: boolean}`. Batches accept 1–20 calls. API input values must be JSON-serializable objects. Settings save merges partial TTL groups. Omitting `token` preserves it; an empty token removes it. A pasted `Bearer ` prefix is stripped. The popup saves a blank token field by omitting it and has a separate removal button.

All messages require this extension's sender ID. Settings writes and cache administration additionally require the sender URL to equal the packaged `popup.html`. Player summaries require a WarEra game-page sender URL or the popup. Query/batch messages remain available to this extension's contexts. There is no externally connectable message handler.

Display reads additionally allow WarEra content contexts; display writes remain popup-only. The worker broadcasts `{type: "WE_AGO_DISPLAY_CHANGED", display: {marketFontSize}}` to existing WarEra tabs after saving. Content validates the sender extension ID and font range before applying it. The initial display read cannot overwrite a newer broadcast. This exchange contains no API token; trusted storage access restrictions remain in place. Clearing API cache or replacing/removing a token preserves the separate display preference. No new permissions are required.

The player summary reads the saved settings only in the worker. Missing token or user ID returns `{state: "setup"}` without network requests. Otherwise it returns:

```js
{
  state: "ready",
  userId: "saved profile ID",
  profile: { ok: true, result: { data, cached, key, createdAt, expiresAt } },
  equipment: { ok: false, error: { code, message } }
}
```

Both component fields use the same success/failure union. Each is queried independently with `{userId}` so equipment failure does not discard a successful profile. Neither the token nor settings are sent to the content script. `createdAt` is returned for both cache hits and misses, preserving the original fetch timestamp on hits; it is an additive field on existing query/batch results.

Error codes include `TOKEN_MISSING`, `USER_ID_MISSING`, `INVALID_TOKEN`, `INVALID_TTL`, `INVALID_REQUEST`, `INVALID_INPUT`, `INVALID_PROCEDURE`, `FORBIDDEN`, `UNKNOWN_MESSAGE`, `NETWORK_ERROR`, `HTTP_ERROR`, `TRPC_ERROR`, `INVALID_RESPONSE`, and `INTERNAL_ERROR`.

### API and calculations

The existing background client supplies GET-only networking, authorization, and persistent caching without modifications. Requests use:

```js
{ type: "WE_AGO_QUERY", procedure: "itemTrading.getPrices", input: {},
  options: { ttlSeconds: 120 } }

{ type: "WE_AGO_BATCH", calls: [
  { procedure: "tradingOrder.getTopOrders", input: { itemCode: "iron", limit: 10 },
    ttlSeconds: 120 }
] }
```

Prices load once per valid cache snapshot. Orders are fetched only for displayed codes with a positive benchmark, in batches of at most 20. Every market API call explicitly overrides the group TTL to 120 seconds. Content retains only transient response snapshots until their original worker `expiresAt`; persistent caching remains in `chrome.storage.local` through the worker. Failures show unavailable states, remove green indicators, and retry after 30 seconds while visible. An entire failed order batch is unavailable until a later attempt, following the existing worker's all-or-nothing batch contract.

The price map accepts positive finite numeric values and object values containing `averagePrice` or `price`. Standard result data and JSON transformer wrappers are supported. Order books require `buyOrders` and `sellOrders` arrays. Only positive finite prices/quantities whose item code matches the tile are considered. Unknown response shapes are not interpreted as bargains.

- Highest buy = maximum valid buy-order price; lowest sell = minimum valid sell-order price.
- Spread % = `(lowest sell - highest buy) / highest buy * 100`.
- Delta % = `(lowest sell - benchmark) / benchmark * 100`; absolute difference = `lowest sell - benchmark`.
- Green = both fresh snapshots exist and `lowest sell < benchmark`.
- Missing sides/zero or missing benchmark/expired data display `—` for unavailable metrics and do not qualify for green. A valid sell with no buy can still show its benchmark delta.

The API price map is the ticket's average/reference benchmark; the extension does not infer a historical averaging window. These are gross comparisons, not guaranteed executable/net profits. Fees, depth beyond the returned top orders, and execution are not calculated.

Inputs were checked against the [published WarEra schema](https://api2.warera.io/openapi.json). Response adapters follow the structures recorded by the community documentation author for [prices](https://github.com/majimawrks/warera-api-docs/blob/master/specs/itemTrading.getPrices/spec.json) and [top orders](https://github.com/majimawrks/warera-api-docs/blob/master/specs/tradingOrder.getTopOrders/spec.json). Those observations are not an authenticated live-response verification.

- Max worker wage uses the same margin per PP as the base break-even BTC/PP. A zero/negative margin displays **None profitable**. Missing prices, recipes, regions or invalid quantities remain unknown, rather than being substituted with zero.
